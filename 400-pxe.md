# PXE-Boot
This document describes how to achieve the network booting for:
- UEFI + BIOS platforms
- Linux: Ubuntu*, Alpine MVP*, TinyCoreLinux
- Windows: Win11*, Win7*
- Tools: Memtest*, Filezilla

(*) Secure Boot ready

Uses nothing from `/etc/lanparty/env`.

Dependencies: `apt install unzip wimtools python3-venv`
```sh run
apt install -y unzip wimtools python3-venv curl
```

## Test Setup
### MacOS Note (Parallels)
Parallels version 19 is the *last* version to include network boot capabilities, you can configure this by adding the following boot flags on the boot configuration:
```
vm.efi.secureboot=1
vm.bios.efi=1
```

## Setup
### iPXE
iPXE is the heart of the whole project and it is arguably the best PXE bootloader out there.
(Only downloaded once: applying this doc again works offline.)
```sh run
mkdir -p /srv/pxe && cd /srv/pxe
if [ ! -e ipxeboot/x86_64-sb/snponly-shim.efi ]; then
	wget https://github.com/ipxe/ipxe/releases/download/v2.0.0/ipxeboot.tar.gz
	tar xzf ipxeboot.tar.gz
	rm ipxeboot.tar.gz
fi
```

### DHCP: which boot file
dnsmasq (`140-dns-dhcp.md`) tells each client what to load first: firmware that is not
iPXE yet gets the iPXE binary for its architecture, iPXE itself gets the menu script.
`/etc/dnsmasq.d/pxe.conf`
```ini file=/etc/dnsmasq.d/pxe.conf
# Boot files. What serves them is this doc's business.
dhcp-match=set:ipxe,175
dhcp-boot=tag:ipxe,autoexec.ipxe
dhcp-match=set:bios,option:client-arch,0
dhcp-boot=tag:bios,tag:!ipxe,ipxeboot/undionly.kpxe
dhcp-match=set:efi32,option:client-arch,6
dhcp-boot=tag:efi32,tag:!ipxe,ipxeboot/i386/snponly.efi
dhcp-match=set:efibc,option:client-arch,7
dhcp-boot=tag:efibc,tag:!ipxe,ipxeboot/x86_64-sb/snponly-shim.efi
dhcp-match=set:efi64,option:client-arch,9
dhcp-boot=tag:efi64,tag:!ipxe,ipxeboot/x86_64-sb/snponly-shim.efi

# The same for clients that netboot over DHCPv6 instead of DHCPv4. Option 61 is the
# client architecture type (7 = EFI x86-64) and option 59 carries the boot file as a
# URL, so the server address is explicit here and must be bracketed.
dhcp-match=set:ip6_x86_64_efi,option6:61,7
dhcp-option=tag:ip6_x86_64_efi,option6:bootfile-url,tftp://[fd10:10::1]/ipxeboot/x86_64-sb/snponly-shim.efi
```

```sh run
dnsmasq --test
systemctl restart dnsmasq
```

### TFTP: ipxe-tftp
The first file goes over TFTP. dnsmasq's own TFTP server stays off: iPXE's Secure Boot
shim asks for `ipxe.efi` instead of its real second stage on many firmwares, and
`vendor/ipxe-tftp` (its README explains) answers that with the right file per architecture.
`/srv/ipxe-tftp` belongs to root, so the service cannot change its own code; `fbtftp` is
installed once (needs internet).
```sh run
apt install -y python3-venv
install -d /srv/ipxe-tftp
cp vendor/ipxe-tftp/tftp.py vendor/ipxe-tftp/ipxe-tftp.service /srv/ipxe-tftp/
chmod +x /srv/ipxe-tftp/tftp.py
cd /srv/ipxe-tftp
if ! .venv/bin/python -c 'import fbtftp' 2>/dev/null; then
	python3 -m venv .venv
	.venv/bin/pip install --upgrade pip
	.venv/bin/pip install fbtftp
fi
cp ipxe-tftp.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable ipxe-tftp
systemctl restart ipxe-tftp
```

```sh verify
# TFTP serves the tree, and the shim's request for ipxe.efi gets the real snponly.efi
systemctl is-active --quiet ipxe-tftp
t=$(mktemp -d)
curl -sS --max-time 10 -o "$t/menu" tftp://127.0.0.1/autoexec.ipxe
cmp -s "$t/menu" /srv/pxe/autoexec.ipxe || { echo "TFTP did not return autoexec.ipxe"; exit 1; }
curl -sS --max-time 10 -o "$t/first" tftp://10.10.0.1/ipxeboot/x86_64-sb/snponly-shim.efi
curl -sS --max-time 10 -o "$t/second" tftp://10.10.0.1/ipxe.efi
cmp -s "$t/second" /srv/pxe/ipxeboot/x86_64-sb/snponly.efi ||
	{ echo "ipxe.efi after the shim is not x86_64-sb/snponly.efi"; exit 1; }
rm -rf "$t"
```

### The boot menu
The boot menu is the "autoexec.ipxe" file contained in this repo.
Copy it to /srv/pxe
```sh run
cp pxe/autoexec.ipxe /srv/pxe/autoexec.ipxe
```

### Enable the HTTP Download
PXE boot relies on TFTP download and while modern TFTP versions (given they are supported by the firmware) should offer similar performance to HTTP, will just rely on HTTP in general.\
Assuming apache2 was already installed of course (`200-web.md`):
`/etc/apache2/conf-available/lanparty-pxe.conf`
```apache file=/etc/apache2/conf-available/lanparty-pxe.conf
Alias /pxe /srv/pxe
<Directory "/srv/pxe">
    Options Indexes FollowSymLinks
    AllowOverride None
    Require all granted

    <FilesMatch "\.php$">
        SetHandler application/x-httpd-php
    </FilesMatch>
</Directory>

# Deny unattend.xml (might contain product keys)
<LocationMatch "^/pxe/.*\.xml$">
    Require all denied
</LocationMatch>
```

```sh run
a2enconf lanparty-pxe
apache2ctl configtest
systemctl reload apache2
```

```sh verify
# the menu over HTTP is this repository's, and unattend files are never served
cmp -s pxe/autoexec.ipxe /srv/pxe/autoexec.ipxe || { echo "/srv/pxe/autoexec.ipxe differs from the repo"; exit 1; }
curl -fsS --max-time 5 http://10.10.0.1/pxe/autoexec.ipxe | cmp -s - /srv/pxe/autoexec.ipxe ||
	{ echo "http://10.10.0.1/pxe/autoexec.ipxe is not the menu"; exit 1; }
code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 http://10.10.0.1/pxe/any/unattend.xml)
[ "$code" = 403 ] || { echo "an .xml under /pxe answers HTTP $code, not 403"; exit 1; }
```
